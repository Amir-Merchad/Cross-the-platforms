# v1.5 and v2: remaining steps

Designs and plans for roadmap steps 3, 4, 5, 6, 7 and 9, written overnight on 2026-11-05. Steps 1 (iPad Wi-Fi input), 2 (free layout) and 8 (direct sharing) have their own documents. **Every choice below is a call for the owner to check.** Only what can be checked without a device was built; each step says what.

---

## Step 3: Android keyboard and mouse over Wi-Fi

**Goal.** The phone gets the PC's keyboard and mouse with no Bluetooth, as the iPad now does.

**Route (call).** The scrcpy route: Android's wireless debugging lets the PC start a small helper process on the phone (`app_process` with a server jar pushed over ADB), with shell rights to inject input. No root, no accessibility service.
- **Keyboard**: inject `KeyEvent`s with key codes and meta state. Built: `core/src/androidkeys.rs` (HID usage → key code, modifier bits → meta state, snapshot → down/up, release on leave), with a test that every key the router can send has a code.
- **Mouse (call)**: prefer a virtual HID mouse through `/dev/uhid` from the helper, as scrcpy's `--mouse=uhid` does, so Android draws its own pointer and the router's existing relative reports and edge tracker work unchanged. Fallback: absolute pointer injection, which would make the phone's position exact (better than the iPad's estimate), at the cost of a second code path in the router.
- **Transport**: the helper listens on a local socket that ADB forwards; the PC side runs in a service on its own thread, like `ipadinput`, and the engine sends without waiting.

**Costs and risks.**
- Wireless debugging must be on, and Android turns it off after a reboot or on another network (Android 11+). Re-enabling it needs the phone in hand: Bridge shows "Turn on wireless debugging on the phone" with steps.
- Pairing ADB once uses a 6-digit code from the phone's Developer options. That code step can live in Add a device.
- Shipping: the helper jar is a build artefact of `apps/android`, pushed by the PC. ADB itself must ship with Bridge (Apache 2.0) or be found on the PC.

**Plan.** 1. Spike: pair ADB over Wi-Fi from Rust (`adb_client` crate, or ADB's own binary), push a hello-world helper, inject one key. 2. Helper: key injection and uhid mouse. 3. `platform/windows/src/androidinput.rs`, mirroring `ipadinput.rs` (states, keepalive, release on leave). 4. Engine routing: host id `android-wifi:<peer id>`, so several phones work. 5. Hub: states, setup steps. **Not built**: needs a phone and the Android SDK, neither in the cloud.

## Step 4: One-step pairing

**Goal.** Each device is added in one guided flow, not a QR code plus Bluetooth plus USB.

**Design (call).**
- **iPad**: USB pairing covers keyboard, mouse and clipboard (built in step 1). Files then pair with **no camera**: Add a device puts the files pairing code onto the iPad's clipboard through the link the USB pairing made, and Bridge on the iPad pastes it. **Built**: `invite_to_ipad` command, `ClipCommand::InviteToIpad`, the hub's `written_directly` so the code never spreads to other devices, a "Put the code on the iPad" button. Next: Bridge on the iPad could spot a pairing code on its clipboard when it opens and offer to pair, so even the paste tap goes. iOS asks before an app reads the clipboard, so this stays a button. *(Call.)*
- **Android**: one QR scan pairs files and clipboard (works today). With step 3, the same flow continues to the ADB code for keyboard and mouse. The QR could carry the PC's address for ADB too.
- **Phone ↔ iPad**: the iPad shows its own code (built in step 8), the phone scans it.

## Step 5: Control from any device

**Goal.** The phone or iPad acts as a touchpad and keyboard for the PC (and later for each other).

**Design (calls).**
- **Messages**: new control messages on the existing paired, encrypted node link: `Pointer { dx, dy, buttons, wheel }` and `Keys { modifiers, keys }`, in the same shapes as the router's reports. Old peers must ignore unknown messages: today an unknown message fails to parse. The first change is a tolerant parser (an untagged fallback), shipped to every device before any device sends input. Not built, so as not to break today's devices.
- **PC side**: `SendInput` with relative motion; the PC's own router stays in charge (Esc ×3 etc.). Input from a phone is only accepted while that phone's Bridge app is in the foreground, and the PC shows "Controlled by S24+" in the tray.
- **Phone/iPad side**: a full-screen touchpad view (one finger moves, tap clicks, two-finger tap right-clicks, two-finger drag scrolls) and the system keyboard. iPadOS stops sending once the app leaves the foreground: that is accepted. Starting control by edge crossing from the iPad is not possible; it starts from a button.
- **Safety (call)**: input from a peer is refused unless the owner switched it on for that peer in its panel. A lost phone must not be a remote keyboard by default.

**Plan.** 1. Tolerant control-message parsing, all apps, released first. 2. Core messages and a rate limit. 3. Windows `SendInput` injector on its own thread. 4. Touchpad views on iOS and Android. 5. Per-peer switch in the hub.

## Step 6: Screen mirroring

**Goal.** See the iPad's (and later the phone's) screen in a window on the PC; and the PC's screen on the iPad.

**Design (calls).**
- **iPad → PC**: the CoreDevice display stream the spike found (H.264 over RTP through the same tunnel; the spike already starts it and throws the video away). Decode with Media Foundation on Windows, draw in a Tauri window. Costs about 1.3 MB/s and leaves the "viewed remotely" notification on the iPad, and cannot run during a call.
- **Android → PC**: the scrcpy route again (MediaCodec H.264 from the helper of step 3).
- **PC → iPad/phone**: Windows Graphics Capture, H.264 with Media Foundation, sent over the node link (iroh QUIC), shown in the app. Latency target 100 ms on a LAN.
- **Not built**: needs devices to check video. A first spike: decode 5 s of the iPad stream to PNGs on the PC.

## Step 7: Screen extension

**Goal.** The iPad (or phone) becomes a second Windows display.

**Design (calls).**
- Windows needs a virtual display driver (an Indirect Display Driver, IDD). Options: write one with Microsoft's IddCx sample (needs driver signing: an EV certificate, or test-signing mode on the owner's PC only), or bundle an existing open-source signed IDD and drive it. The second is far less work; licence and signing must be checked.
- The virtual display's frames go out exactly as in step 6 (PC → iPad mirroring), and touches or the pointer come back through step 5.
- Extending the iPad's own desktop onto the PC is not possible (no API).
- **Not built.** Highest risk of all steps: driver install and signing.

## Step 9: v2, over the internet

**Goal.** Clipboard and files between the owner's devices when they are not on the same network.

**Design (calls).**
- The node already uses iroh with relay fallback, so paired devices can already reach each other through a relay when hole punching fails. Today's default relays are n0's public ones.
- **Limits**: clipboard only text up to 1 MB over the relay; files over the relay need a confirmation above 100 MB ("This goes over the internet and may be slow"). Input never goes over the internet. *(Calls.)*
- **Privacy**: everything is end-to-end encrypted between paired keys; the relay sees only encrypted traffic and endpoint ids.
- **Own relay (call)**: offer a setting for a self-hosted iroh relay later; not needed to start.
- **Built so far**: nothing new; the plan's first task is a core integration test with two nodes forced through a local relay (iroh's test relay), checking clip and file delivery and the limits. Needs a relay binary in CI.
