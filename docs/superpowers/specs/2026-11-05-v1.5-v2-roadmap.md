# v1.5 and v2 roadmap

The main spec is `docs/specs/2026-11-02-device-bridge-design.md`. This document sets the order of work after the base UI. Each step gets its own design and plan when it starts.

## What the owner asked for

- Keyboard and mouse over Wi-Fi on all devices, so Bluetooth is not the weak point.
- One pairing, not a QR code plus Bluetooth.
- Screens arranged freely: stacked beside or above each other, with no limit of four around the PC.
- Control any device from any device, not only from Windows.
- Screen mirroring and screen extension.
- Sharing directly between all devices, not through Windows first.
- The owner keeps using the app during development and reports problems as they appear.

## Facts that shape the order

- The owner's MT7921 Bluetooth crashes under Bridge's use, and recovery has needed a BIOS reset. Getting off Bluetooth is the most valuable change.
- `idevice` 0.1.68, already a dependency, has `core_device::hid`: keyboard, touch, scroll and buttons sent to an iPad through the same tunnel clipboard uses, with no app on the iPad. Its source says events are dropped unless a `display_stream` media stream is active, so input and mirroring share one foundation. No mouse pointer surface is confirmed yet. This one result overturned the earlier "iPad needs Bluetooth" answer, and it is unproven on the owner's iPad.
- Android can take real input over Wi-Fi through a process started with wireless debugging, as scrcpy does. Setup is more technical than Bluetooth.
- Windows takes input through `SendInput`.
- Bluetooth stays as the option that needs no setup, unless a spike shows it can be retired.

## Order

| # | Step | Why here | Risk |
|---|---|---|---|
| 1 | Spike: iPad input over Wi-Fi | Decides the whole input design, needs no Bluetooth | Pointer may be touch only; latency unknown |
| 2 | Free screen layout | Asked for directly, and every input route uses it | Far-edge crossing relies on dead reckoning |
| 3 | Wi-Fi input for Android and any transport per device | Removes Bluetooth from the daily path | Wireless debugging setup, restart after reboot |
| 4 | One-step pairing | Depends on which devices still need Bluetooth after 1 and 3 | iPad pairing prompt needs a test |
| 5 | Control from any device | Phone and iPad act as touchpad and keyboard for Windows and each other. iPad input is only live while its app is open | Starting edge crossing on iPad is not possible |
| 6 | Screen mirroring | Reuses the iPad display stream from step 1. Then phone and Windows sources | Encoding and latency work |
| 7 | Screen extension | Windows virtual display driver plus the stream from step 6. Extending the iPad's or phone's own desktop is not possible | Driver signing and install |
| 8 | Direct sharing between all devices | Phone and iPad pair with each other; clipboard and files stop going through Windows | Clipboard rules with no hub |
| 9 | v2: internet | Pairing keys and relay already work. Mostly UX and limits | Abuse limits, relay cost |

v1 shipping (installer, signed Android release, merge, tag) can happen whenever the owner wants, between any two steps.

## Calls Claude made (owner to check)

- Native apps stay, and Tauri mobile stays dropped. Background service, share target and clipboard tile have to be native anyway, so Tauri would add a layer rather than remove one.
- Direct sharing is pulled into v1.5 order at step 8, before v2.
- Spec §3 rules out extra hardware. It stays ruled out unless the owner changes it, so USB adapters and ESP32 are not in this plan.
